#### Findings

- **Affected spec:** `specs/adversarial-validate-verifier.feature` — a gap, no scenario covers it
  **Affected scenario:** adjacent to "A report without a non-empty commands-run record fails evidence validation" and to AC2's "dead-subagent stubs and narrated verdicts are refused"
  **Risk:** The shipped `docs/architecture/gatekeeper-prompt.md` Output Format template
  is itself a *passing* report. Its Status line is the legend
  `SAFE | WARNING | CRITICAL`, which `firstVerdict` resolves to `SAFE` (the
  `separators` replacer treats `|` as a token separator), and its example verification
  block already carries a complete grounded record
  (`{"argv":["centinela","validate"],"exitCode":0,"durationMs":84210}`). I copied that
  section verbatim into a report, ran the prompt's mandated `centinela artifact stamp`,
  and `centinela complete` advanced with exit 0 — with `<FEATURE_NAME>` and
  `<current date>` still unsubstituted and every section still placeholder prose. This
  defeats the exact principle the same feature applied to `artifact new`, whose stub
  comment reads "a stub that passed would reintroduce the dead-subagent hole". A
  verifier that writes its prose but forgets to collapse the legend line silently ships
  the passing verdict, and fabricating the record becomes the path of least resistance
  rather than an act of deliberate dishonesty — i.e. the plan's own High "Verifier
  theater" risk, which the plan claims is mechanically mitigated.
  **Suggestion:** Make the template fail-closed exactly like the `artifact new` stub —
  print `**Status:** CRITICAL` in the Output Format and list the vocabulary in prose
  underneath — and/or treat a Status line carrying more than one known verdict token as
  unparseable. Replace the example `commands` entries with obviously invalid
  placeholders so a verbatim copy cannot ground itself.
  Deferred as `verifier-template-status-fail-closed`.

- **Affected spec:** `specs/adversarial-validate-verifier.feature`
  **Affected scenario:** "centinela artifact new followed immediately by centinela complete FAILS" and "A report without a non-empty commands-run record fails evidence validation"
  **Risk:** Both scenarios pass, but only because their fixtures carry no real
  `[validate] commands`. The real ordering inverts the plan's stated rationale
  ("Freshness runs first because it is the cheapest and the one that tells the operator
  to re-verify before they pay for a full suite run"): `runValidateGates` runs
  `executeValidation()` and then claim verification, and only afterwards does
  `wf.Complete` reach `ValidateArtifacts` → `gatereport.Assess`. `VerificationFresh`
  deliberately returns `nil` when `Assess` fails, so an ungrounded report short-circuits
  nothing. I proved this with a marker command: the validate commands executed before
  the block. A dead-subagent stub therefore costs a full `centinela validate` (519 s
  here) plus claim verification before being refused — the cheapest check of all runs
  last, on a step whose `complete` already sits near the runner's wall-clock cap.
  `TestRunValidateGatesStaleVerificationShortCircuits` covers only the stale path, where
  the report is already grounded.
  **Suggestion:** Call the content-only admissibility check (`validateGatekeeper` /
  `gatereport.Assess`) at the top of `runValidateGates`, before `executeValidation()` —
  it is a pure file read. Add a fixture with a marker validate command asserting the
  suite did NOT run for an ungrounded report.
  Deferred as `assess-report-before-full-validate-run`.

- **Affected spec:** `specs/adversarial-validate-verifier.feature`
  **Affected scenario:** the statusline half of Slice 6, behind "Revision skew … demands fresh verification" and "Uncommitted in-place fixes … stale the tree digest"
  **Risk:** `cmd/centinela/hook_statusline_validate.go` maps `"verification is stale"`
  to `STALE_VERIFICATION`/`reverify-fresh-context`, but the only input it classifies
  comes from `workflow.ValidateArtifacts`, which by design (D6) never performs the
  git-backed freshness check — `VerificationFresh` has exactly one caller,
  `runValidateGates`. The branch is dead: an operator whose verification has gone stale
  sees the statusline report `none` / `run-validate` (i.e. "validate is clear") right up
  until `complete` hard-blocks. Worse, `TestValidateStatusBlockGroundedReportClears`
  encodes that misleading state as expected — it asserts `block == "none"` for a report
  stamped `revision:"a", treeDigest:"b"`, stale by construction — so the dead branch
  reads as covered.
  **Suggestion:** Either surface staleness in the statusline (one `VerificationFresh`
  call scoped to the active validate-step feature, so the git cost is not paid per
  workflow per prompt), or delete the unreachable case and document staleness as a
  `complete`-time-only signal.
  Deferred as `stale-verification-statusline-unreachable`.

- **Affected spec:** `docs/plans/adversarial-validate-verifier.md` §8 (dogfooding) — operational, not a Gherkin scenario
  **Affected scenario:** "A legacy in-flight workflow still completes with an old-format validation-specialist report"
  **Risk:** This feature's own workflow file carries no `validateContract` (it started
  before the field existed) and `orchestrationMode: strict-subagents-v1`. Running
  `centinela hook orchestration` in this worktree prints: *"Required evidence before
  centinela complete adversarial-validate-verifier:
  `.workflow/adversarial-validate-verifier-validation-specialist.md`,
  `.workflow/adversarial-validate-verifier-validation-specialist.json`"*. No such pair
  exists — only the `gatekeeper` pair does. So `centinela complete
  adversarial-validate-verifier` will hard-block on missing `validation-specialist`
  evidence, even though `CLAUDE.md`, the new prompt, and the DEPRECATED banner on
  `validation-specialist-prompt.md` all point the operator at the gatekeeper verifier.
  The plan anticipated the legacy *gate* path but not the strict-mode *evidence*
  consequence. This is correct-by-design behaviour producing a surprising outcome, not
  a bug in the gate.
  **Suggestion:** No code change. Before completing this feature, additionally produce
  the legacy pair (`centinela evidence init adversarial-validate-verifier
  validation-specialist`, then `evidence append … inputs` / `outputs`) per the still
  published `docs/architecture/validation-specialist-prompt.md`. Do not hand-edit the
  pinned `validateContract` to dodge it.
